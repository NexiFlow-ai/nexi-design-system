**DS-6904** · `apps/tasks/src/components/inbox/CapabilityRequestCard.tsx#CapabilityRequestCard` · adopted

The one Inbox card for a request a person filed and a builder or administrator decides — the existing `capability_binding` approval with two steps: who asks what for which agent/Project (an `article` named by that line, with the time) · the subject line (`ProviderMark` · API · host · *new integration* / the automation's what · when · using · tells) · the counts with *actions* and *note* disclosures · the connection row with its door (*Connect in Core →*, step 1) · the decision (*Needs changes* with a required note · *Approve* / *Enable*, **enabled only once a healthy connection exists**, with the reason beside it while it waits). An administrator without a Project relation sees the projection only — the agent and the Project by name, never thread content. Not a kit duplicate: the Inbox card idiom of DS-7010 with a gated second step.
